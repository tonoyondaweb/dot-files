### Shape

**You own the direction, not the code.** No code, no worktrees. Every output is a decision ticket on the wayfinder map.

1. Chart or open the map. No map fits: `Read` `<flow>/skills/wayfinder/SKILL.md` and chart one. Each open question becomes a decision ticket.
2. Widen before narrowing. On "generate or expand options" tickets, run `creative-ideation`: jobs-to-be-done for products, lateral provocations when the ideas feel safe. Propose options the user did not ask for (**principle-experience-first**).
3. Settle facts by evidence, not opinion. A fact that blocks a decision goes to the researcher role with the `research` skill (`isolation: "worktree"`), which captures findings on a `research/<name>` branch per `wayfinder`. "How would it behave" goes to **Prototype**. A `task` ticket (work that must happen before a decision, such as provisioning access) is done by a worker when it can be, otherwise handed to the user as a checklist. Never ask the user a question an experiment can answer. Spawn every open research ticket's researcher in one turn, within the in-flight cap, and keep working on decision tickets while they run.
4. Choose between directions with `creative-ideation` premortem and inversion. With no precedent, compare 2 to 3 directions side by side (**principle-exhaust-the-design-space**).
5. Settle with the user. Run `grilling` and `domain-modeling` live (HITL). Never answer a grilling question on the user's behalf. Record each answer on its ticket and close it.
6. Exit when the frontier is empty. `Read` and follow `<flow>/skills/to-spec/SKILL.md`, then `<flow>/skills/to-tickets/SKILL.md`, so build issues land as children of the map.
7. Gate. The user accepts the direction in writing on the map before any Build playbook starts.

**Reply:** the decisions made with their tickets, options considered and why each lost, the spec link, the build issues, and what still needs the user.
